# HufiAgents V1.2 — Architecture Addendum

**Date:** 2026-09-08  
**Base architecture:** existing proven V1/V1.1 core in `ARCHITECTURE.md`  
**Purpose:** define the additive V1.2 layers without rewriting or invalidating historical V1 architecture decisions.

## 1. Architecture rule

V1.2 extends the existing core. It does not replace:

- Mission/Task orchestration,
- Agent Registry,
- Model Router,
- Tool layer,
- Review/Retry,
- Approval/Risk policy,
- Audit,
- Recovery,
- workspace/isolation,
- project/Git connector security.

All new persistence is additive and must preserve V1.1.2 data.

## 3. Work Evidence architecture

Work Evidence is **not** a second audit log.

Audit remains the technical, append-only source of execution history. Work Evidence is a curated, user-facing projection built from real trusted sources.

Suggested conceptual record:

```text
WorkEvidence
- id
- mission_id
- task_id? 
- agent_id?
- team_id?
- project_id?
- evidence_type
- title
- summary
- source_type
- source_id
- artifact_ref?
- created_at
- redaction_state
- visibility
```

Rules:

- every evidence item must have a real source,
- no purely decorative evidence records,
- evidence generation should be deterministic where possible,
- redaction/sanitation occurs before user display,
- raw secret-bearing tool output is not copied wholesale into evidence.

## 4. Company Graph architecture

The company model is a graph with stable node identity.

### Node kinds

- Owner/Human
- Agent
- Team
- Project
- Resource
- ChatRoom

Existing Task/Routine/Artifact entities remain their own execution/domain records and may link to graph nodes.

### Relationship kinds

- `reports_to`
- `member_of_team`
- `works_on_project`
- `responsible_for_resource`
- `may_use_resource`

Membership is many-to-many.

Do not implement the whole model as a single `parent_id` tree.

## 5. Rights boundary

Graph membership describes context and organization; authorization remains governed by the existing capability/risk/approval system.

Examples:

```text
Agent -> member_of_team -> Marketing
```

does not grant Git write.

```text
Agent -> works_on_project -> HufManager
```

does not grant production deploy.

```text
Agent -> may_use_resource -> HufManager repo
```

still cannot exceed the agent/delegator capability/risk ceiling and may require approval for sensitive side effects.

## 6. Chat-room context

Rooms provide bounded contextual addressing without copying the entire company state into prompts.

Room types:

- agent,
- team,
- project,
- company.

A mission/task created from a room may inherit references such as:

```text
room_id
project_id?
team_id?
primary_agent_id?
```

The Context Loader resolves only relevant memory, skills and resources from those references.

## 7. Skill architecture

Skill = reusable procedure.

Suggested conceptual fields:

```text
Skill
- id
- name
- description
- version
- scope_type
- scope_id
- owner_agent_id?
- procedure
- required_capabilities
- input_contract
- output_contract
- risk_ceiling
- source: system|manual|learned
- status: draft|approved|archived
- success_count
- failure_count
- created_at
- updated_at
- last_used_at
```

A Skill never contains credentials and should not be a transcript dump.

## 8. Memory architecture

Scopes:

- user/global,
- agent,
- project,
- mission,
- shared knowledge.

Suggested conceptual fields:

```text
Memory
- id
- scope_type
- scope_id
- category
- summary
- content
- importance
- confidence
- source
- created_at
- updated_at
- last_used_at
```

Memory access must be scope-aware. Cross-project/agent sharing is explicit, not accidental.

## 9. Progressive Context Loader

Input:

- mission/task intent,
- room/project/team references,
- selected agent,
- tool/capability needs.

Resolution order:

1. bounded room/project/team metadata,
2. relevant project memories,
3. relevant agent memories,
4. relevant approved skills,
5. explicit shared knowledge,
6. required tool/capability constraints,
7. compacted recent mission context.

Budgets:

- max memory items,
- max skill items,
- max chars,
- estimated max tokens.

Context compaction/load decisions are auditable.

## 10. Learning Loop

Learning trigger:

```text
mission completed
AND reviewer approved
```

Possible outcomes:

- no reusable learning -> record skipped reason,
- create/update scoped memory,
- propose draft skill,
- update approved low-risk skill/statistics.

High-risk procedures remain draft until appropriate review/approval.

## 11. Cost Governor

Cost Governor is a policy layer around provider calls, not a UI setting agents can bypass.

Track even for local models:

- provider/model,
- calls,
- estimated input/output tokens,
- latency/runtime,
- retries.

Local financial model-call cost is `0 EUR`.

External calls additionally check hierarchical budgets:

- mission,
- agent,
- project,
- day/week/month.

Default V1.2 mission external cost limit: `0 EUR`.

## 12. No-LLM execution

Deterministic routine executor sits below the model layer.

```text
Routine
 -> deterministic capability available?
      -> run directly
      -> normal: persist result/evidence; 0 model calls
      -> anomaly: optional local-model analysis
```

This is required for HTTP/service/disk/SSL/backup/file/Git-state checks where deterministic code is sufficient.

## 13. Credential architecture

Credential values are kept out of ordinary domain records.

Conceptual separation:

```text
Connector/Resource
  -> credential_handle
       -> credential store
```

Normal domain/API objects expose metadata such as:

- connected/not connected,
- provider/type,
- scope/permissions summary,
- created/rotated timestamps,
- optional safely masked hint.

They do not expose raw secret value.

Do not make encryption decisions based on convenience. If secure encryption-at-rest is not available, fail closed and document the missing capability.

## 14. Resource architecture

Resources represent reusable work targets/capabilities such as:

- GitHub repositories,
- servers,
- tools/services,
- later browser/computer workspaces.

Repository metadata can safely include:

- name,
- description,
- visibility,
- primary language,
- last activity,
- repository reference,
- linked projects/teams.

Credential data is not part of resource metadata.

## 15. Frontend/backend contract

Codex owns the implementation contract:

`implementation/V1_2_API_CONTRACT.md`

Claude Code consumes it.

The frontend may organize/visualize entities, but it does not become the source of truth for:

- permissions,
- credentials,
- mission state,
- Work Evidence truthfulness,
- model/cost policy.

## 16. Migration rule

V1.2 database changes are additive.

Must preserve:

- missions,
- tasks,
- agents,
- routines,
- approvals,
- audit history,
- existing V1.1.2 production data.

Migration is validated against a production-shaped DB copy before production deployment.

## 17. V1.3 boundary

V1.2 may define Browser/Computer interfaces, but the real persistent per-agent browser/computer belongs to V1.3.

Therefore:

- V1.2 Work Evidence can use existing files/tests/diffs/PRs/results,
- V1.3 adds real browser/computer screenshots/live preview/handoff,
- V1.2 UI must not fake those later capabilities.

## 18. Acceptance architecture proof

A V1.2 release must demonstrate:

1. migration/data preservation,
2. real local-Qwen mission,
3. real Work Evidence tied to execution,
4. secret-redaction proof,
5. Skill/Memory reuse on repeated workflow,
6. No-LLM routine with zero model calls,
7. Company Graph persistence/multi-membership,
8. room-context correctness,
9. budget-zero external-call block,
10. real frontend/API integration without fake capability state.
