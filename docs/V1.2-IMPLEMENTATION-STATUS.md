# HufiAgents V1.2 — Implementation Status

**Snapshot:** 2026-09-08  
**Production:** `v1.1.2`  
**Backend candidate:** PR #22 — `codex/v1-2-core-capabilities` @ `068fa46b399d7e80acfcfa32147de62de88df5aa`

This document distinguishes what is present in the current Codex candidate from what is still only target/foundation. It should be updated after each meaningful V1.2 integration checkpoint.

## 1. Candidate status

PR #22 currently proposes:

- redacted persistent Work Evidence,
- typed company graph models/APIs,
- teams/projects/resources/relationships/chat rooms,
- scoped skills and memory,
- progressive context assembly,
- reviewer-gated learning,
- basic Cost Governor,
- deterministic no-LLM checks,
- metadata-only credential handles,
- additive persistence migrations,
- initial V1.2 API contract/docs.

GitHub Actions `core` check is green for the current head.

This does **not** mean V1.2 is release-ready. Required real XXL/integration/browser proofs remain.

## 2. Work Evidence — candidate implementation exists

Current candidate includes:

```text
POST /work-evidence
GET  /work-evidence
GET  /work-evidence/{id}
```

`WorkEvidence` contains:

- mission/task references,
- source type,
- evidence type,
- summary,
- content,
- artifact reference,
- metadata,
- timestamps/redaction timestamp.

The persistence boundary sanitizes summary/content/artifact/metadata before storage.

Audit markers include:

- `work_evidence_created`
- `work_evidence_redacted`

### Still to prove

- real Work Evidence created by a real local-Qwen mission,
- production-shaped migration/data preservation,
- frontend evidence cards consuming real records,
- screenshot/artifact sanitation path once real screenshot handling exists.

## 3. Redaction — candidate implementation exists

Candidate redaction expands detection for:

- Authorization/Proxy-Authorization,
- cookies/set-cookie,
- bearer values,
- GitHub/token prefixes,
- password/passwd/token/secret/API-key/client-secret/access-key/private-key/session/cookie assignments,
- credential-bearing URLs,
- private-key blocks.

Unit tests include controlled fake PAT/environment/header/cookie/credentialized-URL cases and a harmless-text non-over-redaction check.

### Still to prove

- controlled end-to-end fake-secret Work Evidence through the real API/runtime,
- screenshot/browser evidence redaction later,
- no regressions/over-redaction in realistic product output.

## 7. Progressive Context — candidate implementation exists

Endpoint:

```text
POST /context/assemble
```

Candidate limits:

- max memory items,
- max skill items,
- max context chars,
- estimated token ceiling.

Context compaction emits `context_compacted` audit evidence.

### Current limitation

The candidate is a bounded relevance/string assembly foundation. It is not yet proof that every real orchestrator/model call uses the new loader correctly.

Required integration proof: repeated real mission with demonstrably selected memory/skill context and reduced unnecessary context/coordination.

## 8. Learning Loop — candidate foundation exists

Current candidate requires:

```text
mission completed
AND all latest task reviews approved
```

Then it can:

- propose a learned skill as draft,
- create scoped memory,
- or record learning skipped.

Audit includes learning/skill/memory markers.

### Still to prove

- real reviewed mission -> learning artifact,
- second mission -> actual reuse,
- unsafe/high-risk candidate handling through full policy/approval integration,
- useful procedure quality rather than only persistence mechanics.

## 9. Cost Governor — basic candidate foundation

Current candidate `CostGovernor`:

- treats local aliases as `0 EUR`,
- estimates external cost,
- reserves against one configured external cost limit,
- blocks when limit would be exceeded.

Unit test proves local reserve is zero and external call is denied at zero budget.

### Not yet complete target

The current candidate diff does **not** yet implement the full target hierarchy of:

- per-agent budgets,
- per-project budgets,
- daily/weekly/monthly budgets,
- provider settlement/accounting,
- full retry/spawn integration,
- actual call telemetry persistence across every provider path.

Therefore this is **FOUNDATION**, not final Cost Governor.

## 10. No-LLM checks — basic candidate implementation

Current deterministic checks:

- HTTP status,
- disk usage,
- file existence,
- Git clean/dirty.

These functions themselves do not invoke a model.

### Not yet complete target

Not shown complete yet:

- service status,
- SSL expiry,
- backup existence as dedicated checks,
- integration into the existing Routine Engine,
- persisted `model_calls = 0` proof for a real scheduled/triggered routine,
- anomaly -> local-Qwen escalation flow.

Therefore the no-LLM capability is currently **FOUNDATION + deterministic primitives**.

## 11. Credential Foundation — deliberately metadata-only

Candidate endpoint:

```text
POST /credentials
```

`CredentialRef` contains metadata only:

- connector,
- label,
- scopes,
- status/timestamps.

It contains no plaintext secret field.

This is a good fail-closed foundation: the docs explicitly state that secure encrypted connector storage remains an integration boundary.

### Still required before real secret storage

- actual encrypted credential store/key-management integration,
- secure write/replace/revoke flow for real values,
- scoped connector resolution from handle -> secret at execution boundary,
- never return raw value through normal API,
- Secret Card frontend integration.

Do not interpret `POST /credentials` in the current candidate as “real token storage is finished”.

## 12. Migrations

Candidate adds schema migrations for:

- Work Evidence,
- Org Graph/Rooms/CredentialRefs,
- Skills/ScopedMemory/LearningRecords.

The intended behavior is additive.

### Still required

Real release proof must run the final migration chain on a **copy of the actual production-shaped V1.1.2 DB** and verify existing missions/tasks/audit/agents/routines/approvals remain intact.

Unit/schema success is not a substitute for that proof.
