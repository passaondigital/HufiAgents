# HufiAgents V1.2 — Product Vision Addendum

**Date:** 2026-09-08  
**Applies to:** `HUFIAGENTS-PRODUCT-VISION.md`  
**Production baseline:** `v1.1.2`

The original Product Vision remains valid as the long-form origin/UX document. This addendum records the product decisions that became binding after the V1.1.2 release and the Grok Bot hands-on experiments.

## 1. The product is now explicitly a Digital Company

The mental model is no longer only “messenger with agents”. It is:

> a simple messenger **plus a living visual company structure** made of digital employees, teams, projects, resources and rooms.

Chat remains the work surface. Org-Canvas becomes the map of the company.

## 2. Company structure is a graph

Do not model the product as a rigid single-parent tree.

An agent may:

- report to a lead,
- belong to several teams,
- work on several projects,
- own/be responsible for resources,
- be allowed to use selected resources,
- participate in several communication rooms.

This allows structures such as:

```text
Pascal
├─ HufiBoss
│  ├─ Marketing
│  │  ├─ HufManager Marketing
│  │  └─ HufiApp Marketing
│  └─ Entwicklung
│     └─ Repo Expert
└─ Mr. EquiBot
   └─ Infrastruktur
      ├─ XXL Server
      ├─ OVH Server
      └─ OpenCloud Server
```

The same Repo Expert may simultaneously belong to Development and work on HufiAgents, HufManager and HufiApp.

## 3. Agents become people-like cards

A normal user sees:

- picture/avatar/photo,
- name,
- one-line responsibility,
- team/project context,
- real status,
- current work when applicable.

A normal user does not see raw agent IDs, provider names, capability JSON or risk codes unless opening technical details.

## 4. Teams, projects and resources are first-class product objects

### Teams

Carry:

- name,
- description,
- members/subteams,
- linked projects,
- routines,
- Teamchat,
- current real activity.

### Projects

Carry:

- name,
- description,
- leads/team,
- linked resources,
- tasks/routines,
- documents/artifacts,
- Projektchat,
- work history.

### Resources

Examples:

- GitHub repositories,
- XXL server,
- OVH server,
- OpenCloud server,
- tools/services,
- later Browser/Computer workspaces.

Repository cards should be visual and scannable rather than rendered as long technical text lists.

## 5. Visible Work is a product law

A non-technical user must be able to trust that work really happened.

Hufi should show real, understandable evidence such as:

- milestone,
- file/artifact,
- test/build result,
- safe diff/commit/PR summary,
- safe server/service result,
- later real browser/computer snapshot.

Never invent work to make the UI look alive.

## 6. Transparency modes

### Einfach

Milestones, important approvals, final result.

### Transparent

Milestones plus sanitized evidence/artifacts.

### Live

Real browser/computer/terminal only when a real session exists.

If live view is unavailable, say so plainly.

## 7. Trust is especially important for the Hufi target audience

The product is intended to be understandable by people who may be excellent horse professionals, craftspeople or solo business owners without being technical users.

The product therefore proves value in their language:

- what was done,
- what changed,
- what result exists,
- what is blocked,
- what needs approval,
- what happens next.

It does not demand trust merely because “AI” is involved.

## 8. Credential UX is part of product quality

Never say:

> Paste your token into the chat.

Use a secure credential card/field instead:

- masked by default,
- temporary reveal if desired,
- after save only connection status/safe hint,
- replace/revoke actions,
- raw value never reappears in normal product state.

A likely token typed into normal chat should be intercepted before send where practical and offered for secure storage.

Backend remains the authority for safe credential handling.

## 9. Drag & drop is organization, not authorization

Dragging a digital employee into a team/project/resource is a simple UX for changing relationships.

It must never silently grant dangerous capability, production write, deployment or raw credential access.

Rights changes remain governed by capability/risk/approval policy and are explained in normal language.

## 10. “What did my team do today?” becomes a core value view

The system should be able to summarize real work by:

- completed tasks,
- teams/agents,
- generated artifacts,
- reviews,
- routines,
- blockers/decisions,
- affected projects.

Time saved/ROI is shown only when measured or clearly labeled as an estimate with a documented method.

## 11. V1.2 product split

### Codex

Builds truth-bearing backend capabilities:

- evidence,
- company graph,
- skills/memory/learning,
- context loading,
- cost/no-LLM,
- credentials,
- APIs/migrations/tests.

### Claude Code

Builds the understandable surface:

- Org-Canvas,
- cards/views,
- drag/drop,
- chats,
- evidence UI,
- transparency modes,
- credential UX,
- responsive/accessibility QA.

## 12. V1.3 boundary

Persistent browser/computer is not a V1.2 finished capability.

V1.2 must be truthful using evidence already available from files/tests/git/reviews/routines.

V1.3 adds:

- persistent browser/computer,
- real screenshots,
- live preview,
- user handoff,
- reset/snapshot/recovery.

## 13. Updated one-sentence brief

> HufiAgents should feel like a simple messenger connected to a living digital company: you see who works for you, organize teams and projects visually, ask for outcomes in normal language, and can verify real work without having to understand the technical system underneath.
